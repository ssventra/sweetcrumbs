Part 1

The website: Sweet Crumb Bakery

Sweet Crumb is a fictional neighborhood bakery. Customers can browse the menu with filters, search, and allergen labels; see today's specials and whether the bakery is open right now; save a pre-order list and send it by email; and request a custom cake. The owner keeps everything current by editing one JSON file: menu items, prices, sold-out status, specials, opening hours, and announcements.

It is plain HTML, one CSS file, and five vanilla JavaScript modules. There is no framework, no build step, and no backend, and it deploys to GitHub Pages or Netlify as-is.

Pages and what they do

Home & VisitHero, featured items, today's specials, weekly hours with "Open now / Closed now", address, map, directionsUS3 (P3)

Architecture

Each page loads exactly one JavaScript module. Imports only go one way, so there are no circular dependencies:

site.js← form.js← cart.js← menu.js← filters.js

site.js imports nothing. It loads and normalizes the menu, handles the bakery's time zone, prices in integer cents, and the header count on every page.

Decisions worth discussing

  • Bakery time zone, not the visitor's. "Open now", today's specials, and pickup lead times are computed in America/New_York, so a visitor in Tokyo sees the right answer.
  • Content can't drift into HTML. The audit fails the build if any menu item name appears in a page.
  • Graceful failure. A broken menu.json shows "Our menu is being updated. Please call us." Blocked browser storage keeps the list in memory with a notice.
  • Money in cents. Prices are typed as dollars and converted to integer cents before any arithmetic.

The 5 clarification decisions

QuestionAnswer
Where do hours and contact details live?In menu.json, next to the menu (one file to edit)
Can an item have several sizes or prices?No: one price plus an optional unit label
Can cake requests attach inspiration photos?No: describe the design in text
Is the pre-order list a page or a panel?Its own page, with a header count
Support dated holiday closures?No: weekly hours plus a free-text announcement

What the analysis caught

  • The spec said "visitor's local time" while the plan used the bakery's time zone.
  • The accessibility gate (Lighthouse ≥ 90) could pass with violations. It was raised to 100.
  • A circular import between site.js, menu.js, and cart.js, fixed by making site.js a base module.
  • The announcement would have rendered twice on four pages.
  • Deploy permissions were granted to the whole workflow instead of only the deploy job.

Part 4

The bakery-qa extension and its two commands

The constitution says no feature is done until it passes "the bakery-qa extension checks", but no such extension existed. I built the checks as a Node suite in qa/, then packaged it as a Spec Kit extension in extensions/bakery-qa/, following the format of Spec Kit's own bundled extensions. The manifest passes Spec Kit's validator.

The extension adds no logic of its own. Each command runs an existing qa/ script and reports the result as a table, so the same checks also run in CI.

1 · speckit.bakery-qa.menu-check

Validates site/data/menu.json, the file the owner edits.

  • Errors: missing or wrong-typed fields, duplicate ids, prices with more than 2 decimals, missing image files or alt text, opening time not before closing, invalid time zone, no open days
  • Warnings: unknown category or allergen, empty category, featured item that's sold out
  • Exit codes: 0 pass · 1 errors · 2 couldn't run (with line and column for broken JSON)

2 · speckit.bakery-qa.site-audit

Runs three stages against the published site/ folder.

  • Unit tests with Node's built-in test runner (7 files, 58 tests)
  • Static audit of every page: metadata, landmarks, image alt/size/WebP budgets, lazy loading, links that resolve, labelled form controls, one module script per page, no hard-coded menu items, and footer contact details matching menu.json
  • Lighthouse CI (mobile, 3 runs per page): Performance, Best Practices, SEO ≥ 90; Accessibility = 100

The first Lighthouse run failed, and that was the gate working

On the first full run, Menu scored 87 and Visit 85 for Performance. Lighthouse blocked the build. The cause was layout shift, not speed: content rendered from menu.json pushed the allergen notice (Menu, CLS 0.252) and the map (Visit, CLS 0.289) down the page after it had painted.

The fix was to reserve space for the rendered content. I measured layout shift on every page at phone and desktop widths, then reran the gate. Both pages went to 100, and CLS is now 0.000 everywhere.

Part 7

Verification and open items

Checked beyond Lighthouse

  • About 120 scripted browser checks in headless Chrome, one script per user story
  • The pre-order list survives a real browser restart (same profile, relaunched)
  • Visitors emulated in New York and Tokyo see the same "Open now" status and specials
  • All four cake-form paths: no service set up, service succeeds, service fails, spam trap
  • Every page at 320, 640 (≈ 200% zoom), 768, and 1280 px: no sideways scrolling, all controls ≥ 44 px
  • Keyboard: skip link, filters, focus moved to error summaries and confirmations
  • Owner edits made only in menu.json appeared on Menu, Home, and Pre-order
  • A clean copy of the repo with a fresh npm ci passes the gate

Still needs a person

  • T060 Screen-reader pass with VoiceOver or NVDA. Automated tools can't confirm everything.
  • T063 Firefox, Edge, Safari, and iOS Safari. Only Chrome could be automated on the build machine.
  • SC-003 Time a non-technical owner following the guide (target: under 10 minutes).

Each has a checklist in specs/001-sweet-crumb-website/checklists/. These two tasks were left unchecked rather than marked done.

Issues found and fixed during the build

  • Duplicate element ids when an item appeared twice on Home
  • "Added to pre-order" was announced but not visible; it is now a toast
  • Broken-image text overlapped a missing team photo
  • The prompt log was recording background notifications
